# Architecture

See the root [README](../README.md) for setup, the [API reference](./api.md) for endpoints, and [deployment](./deployment.md) for AWS/CDK details.

## Data Model

- **User**: email, name, avatar, role (ADMIN/USER), Google/Cognito IDs
- **Post**: title, slug (auto-generated), excerpt, content (HTML), cover image, status (DRAFT/PUBLISHED), publishedAt (enables scheduling)
- **Tag**: name, slug — many-to-many with posts via `TagsOnPosts`. Created implicitly on post save (upsert by slug); admin-managed after the fact via `PATCH`/`DELETE /tags/:id` (rename, merge-on-collision, delete) — see "Tag rename merges into an existing tag" below
- **Comment**: content, approved flag, belongs to user and post; optional self-relation `parentId` (one level of threading — a reply can't itself be replied to) and `isOwnerReply` flag (masked to the "Broomn" persona in public responses, see "Reply as Broomn" below)
- **Newsletter**: email, status (PENDING/CONFIRMED/UNSUBSCRIBED), optional user link, `blockedAt` (nullable — admin block, orthogonal to `status`; see "Blocking a newsletter subscriber" below)
- **Media**: filename (S3 key), original name, mime type, size, public URL — many-to-many with posts via `MediaOnPosts`, with the About page via `MediaOnAboutPage`, and with the Support page via `MediaOnSupportPage`, kept in sync automatically whenever a post's, the About page's, or the Support page's content is saved (see `syncMediaUsage` in `post.service.ts` / `about.service.ts` / `support.service.ts`)
- **AboutPage**: content (HTML) — a singleton, exactly one row (seeded by migration), no title/tags/scheduling; many-to-many with media via `MediaOnAboutPage`
- **SupportPage**: content (HTML) — a singleton, exactly one row (seeded by migration), no title/tags/scheduling; many-to-many with media via `MediaOnSupportPage`

## Authentication Flow

1. User clicks "Sign in with Google" → redirected to Cognito Hosted UI
2. Cognito handles Google OAuth → redirects back with authorization code
3. Frontend exchanges code for tokens via Cognito's token endpoint
4. Frontend sends the Cognito ID token to `POST /auth/google`
5. API verifies the ID token using Cognito's JWKS public keys
6. API upserts the user in the database and issues its own JWT pair:
   - **Access token** (15 min) — sent on every request
   - **Refresh token** (7 days) — used to get new access tokens

## Architecture Decisions

### Cursor-based pagination

All list endpoints (`/posts`, `/posts/:postId/comments[/all]`, `/comments/admin`, `/newsletter/subscribers`, `/media`, `/tags/admin`) use cursor pagination instead of `OFFSET`/`page`: the client passes `cursor` (the last-seen row's `id`) and gets back `{ data, meta: { nextCursor, hasMore } }`. This avoids two problems `page`/`skip` has at scale — the database has to walk past all skipped rows on every request (so page 500 costs far more than page 1), and rows can be duplicated or skipped across pages if data changes between requests.

- `api/src/lib/pagination.ts`'s `paginateWithCursor` fetches `limit + 1` rows to derive `hasMore` without a separate `COUNT(*)`.
- Every query orders by `[{ <field>: 'desc' }, { id: 'desc' }]` — the `id` tiebreaker is required because the primary sort field (e.g. `createdAt`) isn't unique; without it, rows with identical timestamps could be skipped or repeated across pages. Verified empirically against real Postgres with intentionally-tied timestamps, not just mocked unit tests.
- The API is forward-only (no `direction`/backward cursor) — the frontend's `useCursorPagination` hook keeps a client-side history of visited cursors so a "Previous" button works without the backend needing to support it, the same approach Stripe's and GitHub's APIs use.
- This trades away numbered-page jumping (no more "go to page 47") and any endpoint-wide `total` count. Where a total/breakdown is still genuinely useful for a dashboard (newsletter subscriber counts by status, admin comment moderation count), it's a separate, cheap indexed `COUNT()`/`groupBy` — unrelated to how deep the cursor pagination goes, so it doesn't reintroduce the scaling problem.
- The public `GET /tags` deliberately stays unpaginated, unlike its admin sibling `GET /tags/admin`. It powers the tag-filter chip cloud (`SearchAndFilter.tsx`) on the public blog, which needs every tag at once to render as a filter widget — pagination would make no sense there, the same way it wouldn't for a `<select>`'s option list. `/tags/admin` exists specifically because the admin tag management page (`/admin/tags`) is a genuine browse-a-list UI, not a filter widget.

### Post scheduling via publishedAt

Rather than a simple boolean "published" flag, we use a `publishedAt` datetime combined with a `status` enum. A post is visible when `status = PUBLISHED AND publishedAt <= now()`. This means:
- Set publishedAt to now → immediately visible
- Set publishedAt to a future date → scheduled, becomes visible automatically at that time
- No cron jobs needed — the query handles it

### Tag rename merges into an existing tag

Tags are created implicitly whenever a post is saved — `buildTagConnections` (`api/src/repositories/post.repository.ts`) upserts by slug for each name typed into the post editor's tag picker, with no admin step in between. That means a typo (`"phytography"`) becomes a permanent `Tag` row the instant a post is saved, and previously had no way to be fixed or removed — it would keep showing up in the public tag-filter chips (`GET /tags`) forever.

`PATCH /tags/:id` (`tag.service.ts`'s `rename`) fixes this by treating a rename that collides with an *existing different tag's slug* as a merge rather than a conflict error: every post linked to the renamed tag is reassigned onto the existing one (`tag.repository.ts`'s `mergeInto`, skipping any post that already had both, since `TagsOnPosts`' composite primary key would reject the duplicate), then the now-empty source tag is deleted. This is deliberately the *default* behavior, not an opt-in "merge" action, because the overwhelmingly common real case is exactly this: an admin fixing a typo'd tag into the correctly-spelled one that already exists from an earlier post. Both the rename-on-save upsert and this endpoint share one `slugify()` (`api/src/lib/slugify.ts`) — they have to produce identical slugs for the same name, or a rename could fail to detect a collision that the next post save would create anyway.

`DELETE /tags/:id` doesn't block on the tag still being attached to posts — it's allowed unconditionally, and `TagsOnPosts`' `onDelete: Cascade` cleans up the join rows. The admin UI (`/admin/tags`) surfaces the post count in the delete confirmation instead of gating on it, since forcing a manual "remove from every post first" step would just be friction for what's usually a deliberate cleanup action.

### HMAC tokens for newsletter

Instead of storing confirmation tokens in the database, we generate HMAC tokens: `base64url(subscriberId + ":" + hmac(subscriberId, secret))`. The token can be verified without a database lookup, and there's nothing to expire or clean up.

### Blocking a newsletter subscriber

`NewsletterSubscriber.blockedAt` is a single nullable timestamp — `null` = not blocked, set = blocked — rather than a separate `blocked Boolean` (which could disagree with `blockedAt` if one write updates one and not the other) or a 4th `status` enum value (which would conflate "blocked" with "current lifecycle status"; a blocked address is still meaningfully "unsubscribed" from the reader's perspective, but "blocked" needs to survive independently of whatever `status` does next).

- **Admin block** (`PATCH /newsletter/subscribers/:id/block`): sets `blockedAt` and `status: 'UNSUBSCRIBED'` in one write — stops delivery immediately.
- **Admin unblock**: clears `blockedAt` only — `status` is left as `UNSUBSCRIBED`; re-subscribing afterward is a separate, explicit action, not implied by unblocking.
- **Self-service unsubscribe** (the existing HMAC token-link flow) only ever touches `status`, never `blockedAt` — this is what makes "unsubscribe but stay blocked" work for free with zero special-casing: a self-unsubscribe on an already-blocked row leaves `blockedAt` in place.
- **`subscribe()`** checks `blockedAt` before its usual upsert and rejects instead — without this, resubmitting the subscribe form would silently reset a blocked row's `status` back to `PENDING`, undoing the block.
- **`getConfirmedSubscribers()`** (used by `send()`) filters `blockedAt: null` too, as defense-in-depth alongside the `status` filter — a send should never depend on a blocked address also being `UNSUBSCRIBED` elsewhere holding true forever.
- No block-reason/audit-log table — the single timestamp covers everything above.

### Comment moderation

Comments are created with `approved = false` by default. They only appear publicly after an admin approves them. Comment owners can delete their own comments; admins can delete any comment.

A user can have at most `MAX_PENDING_COMMENTS_PER_USER` (default 15, `api/.env.example`) comments awaiting moderation at once — `commentService.create` counts the user's unapproved comments and returns a 429 once the cap is hit, with a translated message on the frontend telling them to wait for existing comments to be reviewed. This is a second layer on top of the per-user rate limit (10/min) below: the rate limit caps posting *speed*, this caps standing *volume* — without it, a user could stay just under the rate limit and still flood the moderation queue with hundreds of pending comments over time.

### Reply as Broomn (identity-masked admin replies)

The admin replies to comments under the "Broomn" persona while staying logged in with their real Google account — no second "Broomn" `User` row exists, since that would just relocate the identity problem rather than solve it.

- `Comment.parentId` (self-relation, nullable) gives one level of threading — a reply can't itself be replied to (`commentService.replyAsBroomn` rejects with `invalid_parent` if the target already has a `parentId`).
- `Comment.isOwnerReply` is set only by `commentRepository.createReply`, called from the admin-only `POST /comments/:id/reply` route.
- **Masking happens server-side, in the repository** (`maskOwnerReply` in `comment.repository.ts`), applied to every row (and nested reply) returned by the public `GET /posts/:postId/comments` endpoint — not just hidden in the UI. If `isOwnerReply` is true, the real `user` relation is swapped for a fixed `BROOMN_PERSONA` object (`{ id: null, name: 'Broomn', avatarUrl: '/images/logo.png' }`) before the response is ever serialized, so a direct API client can't see the real name/avatar either. Admin-only endpoints (`/comments/admin`, `/posts/:postId/comments/all`) skip masking — moderation needs the real identity.
- Owner replies are auto-approved (`approved: true` at creation) — the moderation queue exists to filter random visitor spam, not the trusted site owner's own replies.
- **Notifying the original commenter** reuses the existing SES `sendEmail` client directly — a one-off transactional email linking back to the post. This does *not* reuse the newsletter's HMAC-token link pattern: that pattern exists so a public link can *verify and mutate* state (confirm/unsubscribe) without a database lookup, but a reply notification just links to an already-public post page — there's no state-mutating action to protect, so the extra token would be complexity without a purpose. Best-effort: a failed send doesn't undo the reply, which is already persisted.

### Translation chunking respects MyMemory's per-request limit

Posts, About, and Support are all written in Portuguese, with an optional admin-authored (or admin-triggered-then-reviewed) English column. Nothing in any public request path calls MyMemory anymore — translation only ever happens from an explicit admin "Translate" button click, in the editor, via `frontend/src/lib/translate.ts`'s `translateHtml`/`translatePlainText`, which has a hard ~500-char limit per request. Content is split into chunks under that limit and translated independently, then rejoined. The splitter first breaks HTML between block-level elements (`p`, `h1-6`, `li`, `blockquote`, `div`, `figure`, `pre`) — always safe, since a boundary between blocks can't land inside a tag — then, for any single block still over the limit (e.g. one long paragraph), splits further at sentence boundaries, but only where inline-tag nesting is balanced (tracked via a running open/close-tag depth counter), so it never cuts through the middle of a `<strong>`/`<a>`/etc. that spans a sentence break. Falls back to a raw length-based cut only if no safe boundary exists at all (e.g. one inline tag alone longer than the limit) — accepted as a rare edge case that doesn't occur in practice for Tiptap-authored prose. Requests also pass a contact email (`de=`) to MyMemory, raising the daily quota from 5,000 to 50,000 words — chunking a long post means more requests for the same content, so the headroom matters more than it used to.

**The sentence-boundary path had a real bug for a while, silently never engaging.** `findSafeSplitPoints` scanned each block's raw string *including* its own outer wrapper tag (e.g. the `<p>` around everything) and started its depth counter at 0 — but that outer tag isn't an inline mark, and the code had no way to tell it apart from one, so depth went to 1 right at the start and never returned to 0 anywhere inside the block's real text. The "only cut where depth is 0" rule then never found a valid point, no matter how many real sentence breaks the text had, and every oversized block silently fell back to the raw length-cut path — not just the rare "one giant inline tag" case that fallback was meant for. Fixed by stripping the block's own outer wrapper before scanning (so depth genuinely starts at, and can return to, 0) and offsetting the returned split points back by the stripped prefix length. Caught by tracing the existing regression test through the real function and finding a mid-word cut where several legitimate sentence boundaries existed — none of the tests at the time asserted *where* a cut landed, only that chunks stayed under the length limit and rejoined correctly, so both the buggy and fixed behavior looked identical to them.

### Image captions live in post content, not as media metadata

Captions are tied to one specific occurrence of an image in one specific post's content — not a property of the image/media asset itself, since the same uploaded image can be reused across posts (or twice in one post) with a different caption each time. Storing a caption as a column on `MediaOnPosts` was ruled out: `syncMediaUsage()` (`api/src/services/post.service.ts`) blindly deletes and recreates that join table's rows on every post save based on a regex scan of the content, so any caption stored there would be wiped on the next save, and one join-table row can't represent two different captions for two occurrences of the same image anyway. Captions live inline in the post's HTML instead, as `<figure><img>...<figcaption>` — tied to the exact occurrence by construction, no schema or migration changes needed, and `syncMediaUsage`'s filename regex finds the image regardless of what wraps it.

Authored via two custom Tiptap node types (`frontend/src/components/tiptapFigureImage.ts`): `figureImage` (`<figure>`, reusing the existing `image` node unmodified as its first child) and `caption` (`<figcaption>`, plain editable inline content) — both use plain declarative `renderHTML`/`parseHTML`, no custom NodeView. `RichTextEditor`'s `insertImage(url)` handle keeps its exact signature but now runs a `setFigureImage` command instead of `setImage`, built the same `chain().focus()....run()` way, which is what carries over the insert-at-cursor guarantee for free. After inserting, the cursor moves into the new empty caption via `tr.mapping.map(pos, -1)` (mapping the pre-insert cursor position through the transaction's own step mapping) rather than hand-computed offsets, since `replaceSelectionWith` can split a surrounding paragraph — a block node can't sit inside a paragraph's inline content — shifting positions in ways fixed arithmetic gets wrong.

### About page is a singleton, not a Post

The About page (`/about`, admin editor at `/admin/about`) is deliberately its own model rather than a `Post` with a reserved slug — it doesn't need tags, a publish/schedule workflow, or listing/search, and reusing `Post` would mean filtering it out of every place that lists or searches posts. `AboutPage` has exactly one row, seeded by its migration so `/about` never 404s waiting for an admin to save content the first time; the API only ever finds-or-updates that row, there's no create/delete. It reuses the same public rendering component (`PostContent`) as posts, and its own admin editor is `ContentLocaleFields` (`frontend/src/components/ContentLocaleFields.tsx`) — a smaller sibling of the post editor's `PostLocaleFields`, single `content` field instead of title/excerpt/content, same PT/EN tabs + Translate button. It has its own `MediaOnAboutPage` join table — mirroring `MediaOnPosts` — so the media library's usage counts, the media detail panel, and "replace this image everywhere" all correctly account for images used on the About page too.

### Support page mirrors the About page pattern

The Support page (`/support`, admin editor at `/admin/support`, linked from the footer as "Diga Obrigado"/"Say Thanks") is the same singleton pattern as the About page, model-for-model: `SupportPage` + its own `MediaOnSupportPage` join table, `support.repository.ts`/`support.service.ts`/`support.controller.ts`/`support.routes.ts`/`support.schema.ts` mirroring the `about.*` files exactly (including a private `syncMediaUsage` copy in `support.service.ts` — kept separate rather than shared, same reasoning as About's own copy). It lists free ways to support the blog (sharing, commenting, subscribing) plus optional Pix/Buy Me a Coffee/PayPal links, entered by the admin through the editor — none of that content, or any payment credentials, lives in source control. `media.routes.ts`'s usage-count, media-detail, and "replace this image everywhere" logic accounts for `MediaOnSupportPage` alongside `MediaOnPosts`/`MediaOnAboutPage`.

### Social share buttons are pre-filled links, not API integrations

`<ShareButtons>` (`frontend/src/components/ShareButtons.tsx`), shown on every post page under the title/tags row, has no server-side component at all — it's pure client-side URL construction (`frontend/src/lib/shareLinks.ts`) plus `window.open(url, '_blank')`, deliberately avoiding OAuth or any platform API (no app registration, no rate limits, no token storage). X, Facebook, LinkedIn, and WhatsApp all support a "share intent" URL that pre-fills their own compose UI with the post's title and link — the user still clicks through and posts manually. Instagram has no such web intent (its API only supports posting via an approved Business app, not a plain link), so its button instead copies the post URL to the clipboard and shows a hint to paste it into a bio/story/DM — same underlying clipboard action as the plain "copy link" button, different copy. There's intentionally no separate admin-only "share to socials" shortcut — admins use the same public buttons on the post page, since a published post is publicly viewable anyway.

### Every indexable page declares its own canonical + hreflang

Google Search Console flagged pages like `/pt` and `/pt/about` as "duplicate without user-selected canonical" — with locale-prefixed routing (`pt`/`en` via next-intl) and no `<link rel="canonical">`/hreflang anywhere in `generateMetadata`/`metadata` exports, Google had to guess which URL among the locale variants (and any redirect/query-string variants of the bare domain) was authoritative, and sometimes guessed wrong. `frontend/src/lib/seo.ts`'s `buildAlternates(locale, path)` builds a self-referencing `alternates.canonical` plus `alternates.languages` (one entry per `routing.locales`, plus `x-default` pointing at `routing.defaultLocale`) from the same static path list the sitemap uses (home, `/about`, `/support`, `/newsletter`, `/posts/:slug`). Every indexable page's `generateMetadata` calls it with `getLocale()` (from `next-intl/server`) and its own static path — it's per-page rather than set once in `[locale]/layout.tsx` because the canonical URL differs per route and a layout can't know which child path it's wrapping. Admin/auth/newsletter-confirm/unsubscribe routes are intentionally excluded — they're either disallowed in `robots.ts` or not meant to be indexed at all.

### History: translation moved server-side, then off the request path entirely

GSC reported `/en/posts/:slug` pages as "Crawled – currently not indexed." The cause: `useTranslatedContent`/`TranslatableTitle` (both `'use client'`) only translated after mount, via a `useEffect` calling MyMemory. The server-rendered HTML any crawler actually received was the untranslated Portuguese original — same `<title>`, same body — for both `/pt/` and `/en/`, byte-for-byte. hreflang correctly told Google these were declared language alternates, but the *content itself* wasn't actually different, so Google's duplicate-content quality assessment still declined to index the `/en/` copy.

The first fix moved translation into the page's async Server Component and `generateMetadata`, via `localizeContent.ts`'s `localizeHtml`/`localizePlainText` (thin locale-gated wrappers around `translate.ts`'s MyMemory calls). This fixed indexing but was still slow and wasteful: every `/en/` pageview blocked on one or more live MyMemory calls (~14s observed for a real post locally), `generateMetadata` and the page body translated the same content independently (double the calls per pageview), and there was no reuse across visitors — the tenth reader of a popular English post paid the same translation cost as the first. `useTranslatedContent.ts`/`TranslatableTitle.tsx` were deleted at this point; `localizeContent.ts` itself was deleted later, once the section below removed its last callers.

### Posts, About, and Support all moved to manual bilingual authoring

Posts moved first, About and Support followed the same pattern shortly after. Admins author (or machine-translate once via an editor button, then review) both languages directly; `/en/` readers just read an already-translated column. **MyMemory is never called in any public request path** — only from an explicit admin button click in the editor.

- **Schema**: `Post` gained nullable `titleEn`/`excerptEn`/`contentEn`; `AboutPage`/`SupportPage` gained nullable `contentEn` (they have no title/excerpt to begin with). `postSummarySelect` (`post.repository.ts`) includes `titleEn`/`excerptEn` (cheap, same as their PT counterparts) but deliberately excludes `contentEn`, mirroring why `content` itself isn't in list payloads — About/Support have no list view, so this doesn't apply to them.
- **Editors**: `admin/posts/[id]`/`admin/posts/new` render `PostLocaleFields` (`frontend/src/components/PostLocaleFields.tsx`, title/excerpt/content per tab); `admin/about`/`admin/support` render the smaller `ContentLocaleFields` (`frontend/src/components/ContentLocaleFields.tsx`, content-only) — a deliberately separate, simpler component rather than `PostLocaleFields` with unused title/excerpt props bolted on. Both share the same shape: PT/EN tabs, both `RichTextEditor` instances mounted simultaneously (the inactive one hidden via CSS, not unmounted, so tab-switching never loses editor state), and a "Translate to [other language]" button that calls `translateHtml`/`translatePlainText` directly from the browser and applies the result through the target editor's own `content` prop — routing it through `RichTextEditor`'s existing sync effect and ProseMirror's parser, which drops unrecognized markup as a side effect, rather than writing MyMemory's untrusted HTML straight into form state. Both confirm via `window.confirm` before overwriting a non-blank target tab.
- **`translateHtml`** (`frontend/src/lib/translate.ts`) does its own embed-splitting internally (`splitAroundEmbeds`/`isEmbedSegment`) so every caller gets embed-safety for free, and returns `{ html, partial }` instead of a bare string: a chunk that fails to translate falls back to its original-language text rather than discarding the whole document's progress, with `partial: true` surfaced back to the editor as a "please review" note.
- **Publish gating exists only for Posts, not About/Support.** `post.service.ts`'s `DRAFT → PUBLISHED` transition — and only that transition, not every save of an already-published post, since autosave resends `status` every 3 minutes — requires non-blank `titleEn` and `contentEn` (an `isBlankHtml()` helper treats Tiptap's empty-doc `<p></p>` as blank), returning the sentinel `'missing_translation'` (mapped to `400` by the controller) if not. About/Support have **no draft state at all** — a save is immediately live — so there's no equivalent transition to gate on; `contentEn` just stays optional forever there, normalized blank → `null` on save (same `isBlankHtml()` shape, duplicated locally in `about.service.ts`/`support.service.ts` rather than shared, matching those two services' existing deliberate non-sharing of `syncMediaUsage`).
- **Media consistency**: all three `syncMediaUsage` copies (`post.service.ts`, `about.service.ts`, `support.service.ts`) scan `content + contentEn` (not just `content`) when rebuilding their junction table, and `PATCH /media/:id/replace` rewrites the image URL in both fields for all three — otherwise an image used only in the English body would show a false `usageCount: 0` and could be deleted while still live on `/en/`.
- **Public rendering**: none of `posts/[slug]/page.tsx`, `about/page.tsx`, `support/page.tsx` call any translation function — each renders `*En ?? <pt field>` directly. When the English field is null, the PT content renders as-is with an "English version not available yet" badge (`PostContent`'s `isPtFallback` prop, `post.ptFallbackBadge` i18n key — shared across all three pages via the same component), `generateMetadata` sets `robots: { index: false }`, and `buildAlternates` (`frontend/src/lib/seo.ts`, takes optional `includeEn`/`canonicalLocale`) drops the `en` hreflang entry and canonicals the page at its `/pt/` URL instead — deliberately reproducing none of the duplicate-content failure mode the first fix above addressed. `PostContent.tsx` itself lost its `translated`/`translationError` props once these were its only callers and none of them needed live-translation-error reporting anymore.
- **Sitemap**: `sitemap.ts` skips a post's `/en/posts/:slug` entry using `titleEn` presence as a lightweight proxy for "has a translation" (avoids pulling `contentEn`'s full HTML into the list-query path; gated together with `contentEn` at publish time, so the two rarely diverge). For About/Support (static, non-DB-row sitemap entries) it does two extra singleton `fetch()` calls against `/about`/`/support` to check `contentEn` directly, defaulting to "include" on any fetch failure — same graceful-degradation stance as the existing posts-list fetch.
- **The home page's post list** (`frontend/src/components/PostCard.tsx`, renamed from `TranslatablePostCard.tsx`) dropped its on-mount MyMemory call entirely — it renders `post.titleEn ?? post.title` from the list response, with the same amber "translation unavailable" badge as before, shown whenever `titleEn` is absent instead of on a live-call failure.
- **No automated backfill for any of the three.** Existing content has no `*En` until an admin opens it and clicks Translate — until then it shows the PT-fallback/noindexed state above, which is the intended interim state, not a bug.

### Raw HTML/script embeds — and why they're excluded from translation entirely, not just protected by a placeholder

The rich text editor (Tiptap, `frontend/src/components/RichTextEditor.tsx`) has no way to preserve a pasted `<script>` tag (e.g. a "Buy Me a Coffee" widget snippet on the Support page) — ProseMirror's paste parser doesn't recognize `script` as a node in this schema, so it silently reduces the tag to its escaped inner text. There is deliberately **no HTML sanitization anywhere else in this pipeline either** — not in the API schemas (`support.schema.ts`/`about.schema.ts`/`post.schema.ts` only check `z.string().min(1)`), not in the DB layer, not at render (`PostContent.tsx` does a verbatim `dangerouslySetInnerHTML`). `HtmlEmbed` (`frontend/src/components/tiptapHtmlEmbed.ts`) leans into that fact rather than fighting it: admin-only editing is the actual trust boundary here, not markup filtering, and this app has exactly one admin. Given that, a dedicated escape hatch for raw embeds was added instead of trying to make the shared rich-text pipeline safe for arbitrary script content by half-measures.

An embed is entered once via a toolbar prompt (`RichTextEditor.tsx`'s "Insert HTML/script embed" button — not typed/pasted directly into the document, which would hit the same ProseMirror-mangling problem), stored as a base64-encoded `data-html-embed` attribute on an otherwise-empty, atomic node (`<div data-html-embed="...">`, no children) — never as parsed ProseMirror content, so it round-trips through editor reloads byte-for-byte. In the editor itself, a `NodeView` renders a friendly placeholder ("🔌 Embedded HTML/script — not rendered here") purely for admin UX; that placeholder text never enters the saved `content` string. The real markup only comes back at final render time, via `resolveHtmlEmbeds` (`frontend/src/lib/htmlEmbeds.ts`), called in `PostContent.tsx` right before `dangerouslySetInnerHTML` — so the live `<script>` only ever exists as real DOM content on the actually-rendered public page, never in the DB row, an API response, or mid-translation.

**A placeholder-token approach was tried first and silently failed in production-like testing.** The initial design swapped each embed for an HTML comment (`<!--HTML_EMBED_0-->`) before calling `translateHtml`, meaning to swap the original markup back in once translation finished. MyMemory's API doesn't preserve non-visible-text markers like HTML comments through a translate round-trip — it just returned the surrounding sentence with the comment silently gone, so the embed vanished entirely from `/en/` pages, with no error to catch. Confirmed by live-testing against a real MyMemory call, not just unit tests (the failure only showed up end-to-end — the placeholder swap-back logic itself was unit-testable and passed, since the unit test's mock naturally preserved whatever string it was given). The fix: `translateHtml` itself splits content into alternating text/embed segments (`splitAroundEmbeds`) and translates each text segment independently, never transmitting embed markup to MyMemory at all — not even as a token to swap back. There's no placeholder to survive a black-box third-party API; the embed segment simply never leaves the request. (This split originally lived in the caller, `localizeContent.ts`'s `localizeHtml` — moved into `translateHtml` itself once a second caller, the post editor's Translate button, needed the same guarantee; see "Posts, About, and Support all moved to manual bilingual authoring" above.)

No public page pays any MyMemory round-trip cost anymore, for any content type — that cost now lands once, in the editor, when an admin clicks Translate, not on every reader's request.

### The API host itself is never meant to be indexed

`api.blogdobroomn.com` also showed up in GSC as a 404 — nothing on the site actually links to it (post/media images resolve straight to the S3 bucket URL, `api/src/lib/s3.ts`'s `uploadObject`, never proxied through the API; every other use of `NEXT_PUBLIC_API_URL` is a `fetch()` call, not a rendered link), so Google most likely found the hostname via its own public ACM cert showing up in Certificate Transparency logs and probed the bare root, which 404s (no route registered there, no custom 404 handler). Since GSC verifies this domain via a DNS TXT record (see "The bare apex domain never renders app content" below), it's one property covering every subdomain, API included, even though the API was never meant to be browsed or indexed. `api/src/app.ts` now sends `X-Robots-Tag: noindex, nofollow` on every response (a global `onRequest` hook, registered right after `helmet`) plus a `GET /robots.txt` disallowing everything — belt-and-suspenders, since the header covers any path a crawler might hit but `robots.txt` is what a well-behaved bot checks before requesting anything else on the host at all.

### Per-user rate limiting

The global rate limiter (`@fastify/rate-limit`, 100 req/min default) keys by authenticated user instead of IP when possible: its `keyGenerator` (in `api/src/app.ts`) attempts `request.jwtVerify()` and keys by `user:<sub>` on success, falling back to IP for anonymous requests. It verifies the token rather than just decoding it — trusting an unverified `sub` claim would let anyone dodge the limit by sending a fresh made-up token per request. A few high-abuse-risk routes are tightened further via per-route `config.rateLimit` (which inherits this same keyGenerator): `/newsletter/subscribe` (5/10min, public and a real SES-cost target), comment creation (10/min per user), and media upload (20/min per user).

**Known limitation, accepted for now**: `@fastify/rate-limit`'s default store is an in-memory `Map`, scoped to a single Lambda execution environment. Since API Gateway can spin up multiple concurrent Lambda instances, each with its own independent counter, this is a soft/best-effort limit rather than a mathematically exact global one under concurrent load. A true distributed limit would need a shared store (e.g. `@fastify/rate-limit`'s Redis option, via ElastiCache or Upstash) — real infra/cost disproportionate to this app's actual traffic. Revisit if usage ever grows enough for this gap to matter.

### WAF was attempted in front of the API Gateway, reverted — HTTP APIs aren't a supported WAF resource type

Motivated by a real finding: CloudWatch Logs Insights queries against `/aws/lambda/broomns-blog-api` showed several IPs doing exhaustive, automated probing for `.env`, `.git/config`, AWS/SSH credentials, `service-account.json`, GraphQL introspection, etc. — one IP alone hit 120+ such paths across three sweeps. That traffic reaches the Lambda before the application-level rate limiter above ever sees it (the rate limiter throttles *speed*, it doesn't recognize known-bad IPs or attack signatures), so a WAF layer still has real value here — just not the way this was first built.

A regional `AWS::WAFv2::WebACL` was added with a `CfnWebACLAssociation` pointing at the HTTP API's `$default` stage. It deployed fine in isolation (validated via a synth-only `Template.fromStack()` check beforehand), but the real `cdk deploy` failed: **AWS WAF's `WebACLAssociation` does not support API Gateway HTTP APIs (v2) at all** — only REST APIs (v1), ALB, AppSync, Cognito user pools, App Runner, Amplify, CloudFront, and Verified Access. `BromnBlog-Api` uses `apigatewayv2.HttpApi` throughout, so this was a fundamental incompatibility, not a fixable ARN typo — the isolated synth check validated the CloudFormation *schema* was well-formed, but couldn't catch a resource-type combination AWS itself rejects at deploy time. Because the WAF resources were bundled into the same `BromnBlog-Api` stack deploy as unrelated API changes, the failure rolled back the *entire* stack update, briefly taking the API back to pre-deploy code while the frontend (a separate stack) had already deployed successfully — a real lesson on blast radius from bundling infra-risk changes with app changes in one deploy.

**Reverted** rather than force-fixed under pressure. If WAF protection for the API is revisited, the two real options are: migrate the API Gateway from `HttpApi` to `RestApi` (a bigger, riskier change touching routing/integration throughout `api-stack.ts`), or front the HTTP API with a CloudFront distribution and attach the Web ACL there instead (CloudFront *is* a supported resource type — this is the standard pattern for exactly this situation, but means new infra: a distribution, DNS changes, and re-pointing `api.blogdobroomn.com`).

### Media served via a dedicated CloudFront distribution, not the frontend one

Uploaded media (post covers, media library images) used to be served directly from the public S3 bucket (`api/src/lib/s3.ts`'s `uploadObject`) — no edge caching, full per-request S3 cost, no edge latency benefit for non-US visitors, and originals served unresized/unconverted up to the 5MB upload cap. `infrastructure/lib/stacks/media-cdn-stack.ts` adds a CloudFront distribution on its own subdomain, `media.blogdobroomn.com` — deliberately a **separate distribution** from `FrontendStack`'s, not a new behavior on it: media S3 keys are bare `<uuid>.<ext>` at the bucket root with no path prefix to route a behavior pattern on, and the deploy pipeline already runs a full `/*` invalidation against the frontend distribution on every app deploy (see [deployment](./deployment.md)) — sharing it would flush the entire media cache on every single app deploy, defeating the point of a long TTL.

- **Origin is a plain S3 origin, not Origin Access Control.** The media bucket stays public-read for now (unchanged from before this stack existed — see `storage-stack.ts`). OAC's automatic bucket-policy grant mutates the bucket's own policy resource, which lives in `StorageStack`, not `MediaCdnStack` — wiring that grant against this distribution's ID created a real `StorageStack ↔ MediaCdnStack` circular dependency (confirmed by a failing synth), since the bucket resource would need to know the distribution's ID and the distribution needs the bucket. `S3BucketOrigin.withBucketDefaults` avoids this entirely. Locking the bucket down to CloudFront-only via OAC is a deliberate, separate, later step (issue #87 Part B item 9) — not just for the dependency reason above, but because it's a one-way break for every direct-S3 image URL already baked into sent newsletter emails (SES bakes the composer's HTML, images and all, into each subscriber's inbox at send time — no database backfill can ever reach that). It can't happen until content referencing old-style URLs — including translated `contentEn`, which a first backfill pass deliberately skips (see below) — has been swept.
- **No Origin Request Policy forwarding/varying on `Origin`.** Every image on this site renders via a plain `<img src>` with no `crossorigin` attribute (`PostCard.tsx`, `posts/[slug]/page.tsx`) — a plain `<img>` tag never sends a CORS request, so there's no CORS response to poison by varying the cache key on `Origin`. Doing so anyway would also conflict with `CACHING_OPTIMIZED`, which includes no headers in the cache key at all. CORS headers (`Access-Control-Allow-Origin: *`) are attached anyway via a *static* Response Headers Policy, for future-proofing, since that's safe for public images — the same policy sets `X-Content-Type-Options: nosniff`, cheap hardening given upload content-type is client-declared with no magic-byte verification (`ALLOWED_MIME_TYPES` in `media.routes.ts` — SVG stays excluded there, since SVG on a same-site subdomain would be a stored-XSS vector).
- **Resize + WebP conversion at upload, not read-time format negotiation.** `next.config.ts` sets `images.unoptimized` (no `next/image`), so there's no per-request format negotiation available — `api/src/lib/imageProcessing.ts`'s `convertToWebp` (via `sharp`) resizes to a 2000px longest-edge cap (never upscaled) and converts to WebP once, at upload time, in `media.routes.ts`'s upload handler. `animated: true` preserves GIF frames as an animated WebP rather than collapsing them to a still. This is the actual bigger cost/perf win here — CloudFront's request pricing and its always-free tier likely make raw delivery cost roughly a wash at this blog's volume either way; what wasn't free before was serving full-size, unconverted originals on every request.
- **`sharp` ships a platform/architecture-specific native binary** (the `@img/sharp-<platform>-<arch>` optional dependency resolved into `node_modules`), the same class of gotcha as Prisma's query engine binary — see [deployment](./deployment.md) for the build-host requirement.
- **Media URLs are immutable**, confirmed in the current codebase: every upload gets a brand-new `crypto.randomUUID()` S3 key at the bucket root, and nothing ever re-uploads bytes to an existing key — `PATCH /media/:id/replace` only rewrites which URL a post/About/Support's content *references*, never touches `Media.url`/`Media.filename` itself. This is what makes a long `CACHING_OPTIMIZED` TTL safe: the only way a cached copy can go stale is the object being deleted outright, which is handled by **active invalidation on delete** — `DELETE /media/:id` (`media.routes.ts`) calls `cloudfront:CreateInvalidation` for the deleted object's path (`api/src/lib/cloudfront.ts`), best-effort (same failure-tolerant pattern as the S3 delete beside it), via a `cloudfront:CreateInvalidation` IAM grant scoped to just this one distribution's ARN, not `*`.
- **A CDN makes hotlinking/scraping of public media both cheap for an attacker and metered, uncapped cost for this account** — two backstops address that, both in `media-cdn-stack.ts`: a `CLOUDFRONT`-scoped WAF `WebACL` with a per-IP rate-based rule (unlike the API Gateway attempt below, CloudFront *is* a supported WAF resource type), and an `AWS::Budgets::Budget` (the first Budgets construct anywhere in this app) covering CloudFront + S3 with an SNS-emailed alert at 80%/100% of actual spend and 100% of forecasted spend.
- **URL backfill is one pass, covering `contentEn` too — collapsed from the original two-pass plan.** `api/src/media-url-backfill.ts` (an on-demand Lambda, manual-invoke only, same pattern as the migrate Lambda below) rewrites `Media.url`, `Post.coverImage`, and `Post`/`AboutPage`/`SupportPage.content`/`contentEn` from the old direct-S3 origin to the new CDN origin, everything together in one transaction (`PATCH /media/:id/replace` matches on the exact `Media.url` string, and would break if it and the content columns diverged mid-migration). The original plan deferred `contentEn` to a second, later, narrower sweep — specifically because manual bilingual authoring (see "Posts, About, and Support all moved to manual bilingual authoring" above) might not have shipped yet, and even once it had, most content wouldn't be translated yet. By the time this backfill actually ran, both had already happened — a meaningful amount of content was manually translated before this ever shipped — so the reason for a second pass no longer applied; splitting it in two would have meant two dry-runs, two snapshots, two production runs for no benefit. The backfill defaults to a dry run (row counts + a sample of matched URLs, logged, no writes) and is naturally idempotent: its filters only match rows still containing the old origin, so a row already rewritten (or one that never had it) is untouched on a re-run. Completing this single pass is also what makes the OAC bucket lockdown above safe.

### WAF was attempted in front of the API Gateway, reverted — HTTP APIs aren't a supported WAF resource type

An AWS Cost Anomaly Detection alert in July 2026 (Jul 18–23, $6.58 above expected) turned out to be entirely benign: the VPC's single NAT Gateway (`database-stack.ts`, `natGateways: 1`) billing for the first time after the initial CDK deploy on Jul 18. NAT Gateway bills a flat $0.045/hr in us-east-1 *regardless of traffic*, so its first ~5 days of existence (`0.045 × 24 × 5 = $5.40`) accounted for most of the anomaly on its own — Cost Anomaly Detection's root-cause UI attributed some of it to "Amazon Elastic Block Store" (a known quirk in how it labels NAT/data-transfer sub-charges, not an actual EBS resource).

This prompted a look at whether the NAT Gateway (~$32.85/mo flat, before any per-GB data processing) could be reduced via VPC Endpoints. Conclusion: **only S3 traffic could move off it, for free.** S3 has a Gateway Endpoint (no hourly or per-GB charge) — added to the VPC so `apiFunction`'s media upload/delete traffic (`api/src/lib/s3.ts`) routes to S3 directly instead of through NAT. Secrets Manager and SES only support Interface (PrivateLink) endpoints, which bill per-AZ-hour (~$14.60/mo per service across this VPC's 2 AZs) — adding both to cover every Secrets Manager/SES call would cost *more* than the NAT Gateway itself, not less, and wouldn't even let the NAT Gateway be removed: Cognito JWKS verification (`auth.service.ts`, via the `jwks-rsa` package) is a plain HTTPS fetch to a public well-known URL, not an AWS SDK call, so it can't be routed through a `cognito-idp` Interface Endpoint without deeper client changes — the NAT Gateway stays mandatory for that alone. Given RDS is already `single-AZ` (see [disaster-recovery.md](./disaster-recovery.md)), collapsing the VPC's `maxAzs` from 2 to 1 was also considered and rejected: `natGateways: 1` is already decoupled from AZ count (CDK's per-AZ default was already overridden), so it saves ~$0/mo while adding a second single point of failure on top of the accepted RDS one.

### CI/CD pipeline

**Branch flow**: feature branches → PR into `master` (everyday development) → PR from `master` into `prod` (a deliberate promotion step — merging into `prod` is what triggers a production deploy). Both `master` and `prod` have real GitHub branch protection: a PR is required (no direct pushes, no force-pushes, no deletions), and the CI workflow's three checks (`API`, `Frontend`, `Infrastructure`) must all pass before the merge button is even enabled — this applies to repo admins too (`enforce_admins: true` on both). The one difference between them: `master`'s required status checks are `strict` (the branch must be up to date with the base before merging is allowed), `prod`'s aren't. This repo was made **public** specifically to unlock branch protection: GitHub disables both classic branch protection rules and the newer Rulesets on private repos unless the account has GitHub Pro. The repo's git history was checked for secrets before flipping visibility — none found (no `.env` files, no AWS keys, no private keys were ever committed).

**CI** (`.github/workflows/ci.yml`) runs on every PR/push touching `master` or `prod`: lint + build (which is also the typecheck, via `tsc`) + test for `api`, and lint + typecheck + test + build for `frontend`, and build + test for `infrastructure`. Nothing here touches AWS.

Both workflows' `actions/setup-node` runners pin Node 24 (bumped from 20 after GitHub started emitting a runner-deprecation warning on Node 20; the Lambda *runtime* itself is unaffected and stays on Node 20 — see `NODEJS_20_X` in the CDK stacks — this only affects the GitHub Actions VM running `npm ci`/`cdk deploy`). Verified via clean-container reproduction (`node:24-bullseye`) that the full pipeline — `npm ci`, `prisma generate`, `api/scripts/fetch-migrate-engine.js`, `cdk synth --all` — behaves identically to Node 20.

**Deploy** (`.github/workflows/deploy.yml`) runs on push to `prod` (i.e. after a merge) and replays the manual procedure documented in [deployment](./deployment.md) in order — build frontend via OpenNext, sync static assets to S3, `cdk deploy --all`, invalidate CloudFront, invoke the migrate Lambda — as one automated job. Real Google OAuth credentials are always passed to `cdk deploy` (from GitHub Secrets), so it can never hit the placeholder-credential fallback that once overwrote Cognito's real Google IdP secret (see the footguns in [deployment](./deployment.md)) — every deploy is a full-stack deploy, safely.

**AWS auth**: GitHub Actions authenticates via OIDC (GitHub's `token.actions.githubusercontent.com` provider, already registered in this AWS account for another project) assuming a dedicated IAM role, `broomns-blog-github-deploy`. Its trust policy restricts assumption to `repo:regesmendes/Broomn-s-Blog:ref:refs/heads/prod` only — no other branch, PR, or repo can assume it. No long-lived AWS access keys are stored anywhere. Its permissions are least-privilege, not broad admin:
- `sts:AssumeRole`/`sts:TagSession` on the existing CDK bootstrap roles (`cdk-hnb659fds-*`) — the same mechanism the CDK CLI already uses for the human deploy user; the actual CloudFormation/resource permissions live on those pre-existing bootstrap roles, scoped by CDK itself.

- `cloudfront:CreateInvalidation`/`GetInvalidation` on the one distribution only.
- `lambda:InvokeFunction` on the one migrate Lambda only.

**GitHub repo configuration** (for reproducing this setup, or auditing what's in place): Secrets — `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` (pulled from the live Cognito Google IdP config, not re-typed by hand). Variables (non-secret) — `AWS_DEPLOY_ROLE_ARN`, `AWS_REGION`, `HOSTED_ZONE_ID`, `CLOUDFRONT_DISTRIBUTION_ID`, `FRONTEND_BUCKET`, `MIGRATE_FUNCTION_NAME`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_COGNITO_DOMAIN`, `NEXT_PUBLIC_COGNITO_CLIENT_ID`, `NEXT_PUBLIC_COGNITO_REDIRECT_URI`, `NEXT_PUBLIC_GA_MEASUREMENT_ID`.

### Favicon spinner: three signal sources, and the real bug that took five attempts to find

`frontend/src/lib/loadingIndicator.ts` is a tiny module-level pub/sub (not React context — it's driven from outside any single component tree) combining independent signals into one loading boolean. Getting the route-transition side right took five iterations. The first four all *looked* plausible and passed all unit tests, but none were visible in a real browser — the actual root cause turned out to be a single line, confirmed only by driving a real (headless) Chromium browser against the real dev server with Playwright and instrumenting the click path directly, rather than reasoning about what "should" happen. Kept here in full because the failure modes — and the reason unit tests didn't catch any of them — are worth knowing before reaching for similar tricks elsewhere.

1. **In-flight API request counter** — incremented/decremented by `ApiClient.request()`, the single choke point every API call already goes through, so every existing and future call gets this for free with no per-page wiring. This part worked from the start, but on `localhost` most requests resolve in well under the 200ms show-delay (see below), so in practice it rarely shows anything on its own.
2. **~~Patching `history.pushState`/`replaceState`~~ — abandoned, never fired.** The App Router has no official "navigation started" event, and every client-side navigation goes through these two calls under the hood, so this seemed like a reasonable hook point. It never actually triggered in practice — almost certainly because the App Router's internal navigation code captured its own reference to the original `pushState` before our patch ran, so the patched version was simply never called by Next's router.
3. **~~`RouteLoading` dropped into a route's `loading.tsx`~~ — mounts too late to help.** (`frontend/src/components/RouteLoading.tsx`, wired up at `admin/loading.tsx`.) Next.js does wrap the segment in a Suspense boundary and does mount this as the fallback — that part isn't broken, and it's still in place today as a genuinely useful complementary signal (see point 4's caveat below). But measured empirically (Playwright, console-timestamped mount/unmount against the real dev server): on a cold, never-before-compiled route it mounted **~2.9 seconds after the click**, stayed mounted for only ~300ms, then unmounted. In dev mode, Next can't render the Suspense fallback until it has already resolved enough of the new route's on-demand chunk request to know a fallback is needed — the fallback only covers the last few hundred ms of a multi-second first-visit compile, never the beginning, which is exactly when the user has zero feedback. Not a mechanism failure; a coverage gap.
4. **A global `click` listener** (`watchForNavigationClicks`) was added to close that gap — and initially made things *worse*, in a way none of the 54 existing unit tests caught. `isInternalNavigationClick` had a guard, `if (event.defaultPrevented) return false`, meant to skip clicks some other handler had already cancelled. In the real app this backfired completely: Next's `<Link>` (and next-intl's wrapper around it) *always* calls `preventDefault()` in its own `onClick` before doing a client-side `router.push` — that's just what every real Link click looks like downstream. Confirmed with a Playwright probe (a second `document`-level click listener added purely for diagnosis) that logged `defaultPrevented: true` on every single click by the time *any* listener saw it. The guard rejected 100% of real navigation clicks, unconditionally. It passed all 54 unit tests only because the test helper (`clickOn()` in `loadingIndicator.test.ts`) dispatches a bare `MouseEvent` directly — nothing in that synthetic setup ever calls `preventDefault()` unless a test explicitly does, so the tests never modeled what a real `<Link>` click actually looks like by the time it bubbles.
5. **The fix**: two changes to `frontend/src/lib/loadingIndicator.ts`. `isInternalNavigationClick` no longer bails on `event.defaultPrevented` at all — it isn't a meaningful "someone cancelled this" signal here, it's just what every Link click looks like. `watchForNavigationClicks` now registers its `document` listener with `{ capture: true }` instead of the default bubble phase. This matters independent of the `defaultPrevented` fix: the App Router hydrates directly on `document` (since the root layout renders `<html>`/`<body>` itself), so React's own delegated click listener is *also* on `document`. Two listeners on the same node in the same (bubble) phase fire in registration order, and React's is registered during initial hydration — long before our own `useEffect` runs — so a bubble-phase listener of ours would always run after React's Link handler had already fired. Capture-phase listeners run before *any* bubble-phase listener on the same node regardless of registration order, which is what actually makes this reliable rather than incidentally-timing-dependent.

The "stop" signal for both (3) and (4)/(5) is the same: a `usePathname()`-keyed effect in `FaviconLoadingIndicator`, which only fires *after* the new route has actually rendered.

`FaviconLoadingIndicator` (mounted once in the root layout) subscribes to the combined signal and swaps the tab's `<link rel="icon">` href to a small rotating SVG (data URI, no network round-trip) while any signal is active, restoring the original href once they all clear. There's a 200ms delay before the spinner appears, so a fast request or transition doesn't cause a visible flash-then-restore flicker.

**How this was actually verified** (after four rounds of code-then-ask-the-user-to-test-in-a-real-browser had all failed): a headless Chromium instance (Playwright, manually assembled — no browser or its shared libraries were preinstalled in this sandbox, so `libnspr4`/`libnss3`/`libasound2t64`/etc. were downloaded with `apt-get download` and extracted with `dpkg-deb -x` into a local directory, no root required, and loaded via `LD_LIBRARY_PATH`) drove the real `npm run dev` frontend against the real API, logged in via the `/auth/dev-login` dev-only endpoint, clicked the real "Admin" nav link, and polled `document.querySelectorAll('link[rel~="icon"]')`'s `href` every 100ms. Before the fix: the href never changed from `/favicon.png`, for the entire wait, on every run. After the fix, against a genuinely cold `.next` cache (deleted between runs to force the real first-visit dev-mode compile): the href starts cycling through the spinner's 8 rotation frames (`rotate=0` → `45` → … → `315` → repeat, at the expected ~120ms cadence) around 300ms after the click, sustains for the full multi-second compile, and correctly reverts to `/favicon.png` once the page settles — reproduced on both a fast (warm-cache) and slow (cold-cache) navigation. Two regression tests were added to `loadingIndicator.test.ts` that model a click already `preventDefault()`-ed by an upstream handler (simulating `<Link>`) — both fail against the pre-fix code and pass against the fix, closing the exact gap that let the bug ship past 54 passing tests four times in a row.

One environment note surfaced during this investigation, unrelated to the bug itself but worth knowing for future work in this dev environment: the frontend lives on a `/mnt/d/...` WSL DrvFs mount, and this Next.js dev server's file watcher did not reliably pick up source edits there — a full kill-and-restart of `npm run dev` was needed after each code change for it to take effect, even though the Fast Refresh websocket looked otherwise healthy. This wasn't the cause of the reported bug (the user did full restarts each time too), but it cost real time during re-verification here and is worth remembering if dev-server behavior ever looks stale after an edit on this machine.

### Never conditionally `return null` from a top-level Provider

`ThemeProvider` (`frontend/src/lib/theme-context.tsx`) used to `return null` while waiting for a `mounted` flag to avoid a flash of the wrong theme. Since it wraps the *entire app* in the root layout, this silently suppressed the server-rendered output of **every page** — the whole admin panel and auth flow rendered as blank/not-found in production for a while before this was caught, and it was hard to trace because pages using `next-intl` translations still looked fine (next-intl inlines all message JSON into the RSC payload regardless of whether the page's own HTML rendered, which masked the bug on translated pages). Any provider that wraps the root layout must always render its `children` — do the actual flash-prevention with a synchronous pre-hydration `<script>` in `app/layout.tsx` instead (reads `localStorage`/`prefers-color-scheme`, applies `.dark` before first paint).

### The bare apex domain never renders app content — HTTP-based verification methods don't work here

`https://blogdobroomn.com` (no path) always 307-redirects to `/pt` with an **empty body** — next-intl's locale-redirect middleware fires before any page or layout ever renders, so nothing in the app (a GA snippet, a meta tag, anything) can ever appear in that specific response. This isn't just theoretical: Google Search Console's "Google Analytics" verification method failed with "could not find any Google Analytics tracking codes on the index page" for exactly this reason — Google's verifier deliberately does not follow redirects when checking domain ownership (otherwise redirecting to someone else's already-tagged site would "verify" a domain you don't own). Any other HTTP-content-based verification method (HTML meta tag, HTML file) would fail identically. The fix was a DNS TXT record instead (`GoogleSiteVerification` in `frontend-stack.ts`) — verified at the DNS layer, bypassing the redirect entirely.

### Migration Lambda doubles as an admin console

`api/src/migrate.ts` defaults to `prisma migrate deploy`, but also accepts `{ args, stdin }` in its invoke payload to run arbitrary one-off `prisma` CLI commands (e.g. `db execute --stdin` for a raw SQL statement) against the production database — it's the only Lambda with a network path into the private-subnet RDS instance, so it's the way to do any one-off admin task (like promoting the first user to `ADMIN`) without a bastion host. See [deployment](./deployment.md#running-database-migrations--one-off-admin-sql) for the invoke command.

### DB credentials are fetched live at cold start, not baked in at deploy time

The API and migrate Lambdas used to get a fully-formed `DATABASE_URL` (including the password) baked into their environment variables at CDK deploy time, via a CloudFormation dynamic reference to the DB secret. That stopped working once the DB secret (`broomns-blog/database`) got automatic 90-day rotation (`infrastructure/lib/stacks/database-stack.ts`'s `addRotationSingleUser`) — a baked-in password goes stale the moment the first scheduled rotation fires, silently breaking every DB connection until someone remembers to redeploy. Now both Lambdas call `api/src/lib/dbCredentials.ts`'s `getDatabaseUrl()` at cold start, which fetches the current username/password from Secrets Manager (`DB_SECRET_ARN` env var) and combines them with the stable `DB_HOST`/`DB_PORT`/`DB_NAME` (these don't change on rotation, only the credentials do). Local dev and tests are unaffected — `getDatabaseUrl()` returns `process.env.DATABASE_URL` unchanged whenever it's already set, which is always true outside Lambda. `api/src/lambda.ts` has to defer `require('./app')` until after this fetch resolves (a runtime `require`, not a static import), since `app.ts` transitively instantiates `PrismaClient` at module-load time, which reads `DATABASE_URL` from `process.env` immediately. See [disaster-recovery.md](./disaster-recovery.md#secrets-rotation) for the full rotation story, including why the JWT secret deliberately did *not* get this treatment.

### Internal analytics: request logging must happen in `onSend`, not `onResponse`

The admin analytics dashboard's `RequestLog` rows are written by a global `onSend` hook in `api/src/app.ts`. Under Lambda (`@fastify/aws-lambda` wraps `app.inject()`/`light-my-request`), the response's internal `'finish'` listener can resolve the Lambda invocation *before* an async `onResponse` hook is guaranteed to finish — the execution environment is then frozen and the pending DB write can silently never land. Fastify awaits `onSend` before the reply goes out, so the write is guaranteed to complete (at the cost of one awaited insert of latency on every logged request — a few ms against same-VPC RDS, accepted). The hook swallows its own errors: analytics must never break the request it's observing. It also skips every `/analytics/*` route — analytics never observes itself, excluded at write time, not by filtering reports: the pageview beacon isn't logged as a request, the admin dashboard's own reads don't inflate `RequestLog`, and the `/admin/analytics` pages never become `PageView` rows (the frontend tracker skips them and the pageview endpoint drops them server-side as defense-in-depth).

### Internal analytics: what RequestLog captures vs what PageView captures

`request.user` is set by the rate limiter's `keyGenerator` (which `jwtVerify()`s every request — see "Per-user rate limiting" above), so the `onSend` hook logs *any* request carrying a valid token, whatever the route. But `frontend/src/lib/api.ts` only attaches `Authorization` on calls that explicitly pass a token — public GETs (`/posts`, `/posts/:slug`, `/tags`) never carry one, even for a logged-in user. So `RequestLog` captures authenticated *actions* (comments, admin operations, auth), not content browsing; `PageView` (client-side tracking, registered users only) is what covers page-level browsing. Don't "fix" this by making the frontend attach tokens everywhere — a much bigger blast-radius change than the dashboard needs. `RequestLog.path` stores the matched route pattern (`request.routeOptions.url`, e.g. `/posts/:slug`), not the resolved URL, keeping dynamic-id routes aggregable. Raw rows in both tables are pruned after 180 days by the daily `broomns-blog-analytics-prune` Lambda — a `from` older than that silently returns partial/zero data (the UI carries a note).

### Internal analytics: PageView ordering is server-side, `createdAt` is written at page-leave

A `PageView` row is flushed when the user *leaves* a page (route change, tab hide, or unload), so its `createdAt` is the leave time — ordering by `createdAt` within a session reconstructs the visit order without trusting any client-side clock or sequence number. The displayed "entered at" is computed as `createdAt - durationMs`, display-only. The session id is a `crypto.randomUUID()` kept in `sessionStorage` (one per browser tab session).

### Internal analytics: `fetch keepalive`, not `navigator.sendBeacon`

`sendBeacon()` is the textbook API for unload-time tracking, but it can't attach custom headers — and this API uses bearer-token auth, not cookies, so the beacon could never carry the JWT. Page-view flushes use `fetch(url, { keepalive: true, headers: { Authorization } })` instead, with the known caveat that unload-time keepalive fetches aren't 100% guaranteed to complete on every browser — accepted for a personal blog. The tracking hook (`frontend/src/lib/usePageViewTracking.ts`) also deliberately bypasses `api.ts`'s shared `request()` wrapper, which would spin the global favicon loading indicator on every background beacon (`uploadMedia` set this precedent). The `hidden` visibility trigger matters most: a backgrounded tab never fires `pagehide`, so without it a close-from-background would lose the final page view.

### Internal analytics: capped lists, not cursor pagination

`GET /analytics/users/:userId/sessions` returns a capped, sorted list (`limit` clamped server-side, no further paging) instead of following the repo's cursor-pagination convention — a deliberate deviation. That convention targets ever-growing content lists (posts, comments, media, subscribers); one user's session history is bounded by how much that one person has browsed, and Prisma's native `groupBy(...).orderBy(_max).take(n)` fits it cleanly with no bespoke keyset scheme. The admin routes live under `/analytics`, not `/admin/analytics` — admin-ness is expressed via the `authorize('admin')` middleware, never a URL segment, matching every other admin route (the *frontend* page path `/admin/analytics` is unrelated).

### Internal analytics: requests-by-user pagination is offset-based, computed in memory

`GET /analytics/requests/by-user` originally used the same capped-list approach as sessions above, but the admin dashboard needed real paging and a name/email search once the registered-user count grew past a glance-able list. Prisma's `groupBy` doesn't support cursor pagination (there's no natural unique field to cursor on mid-aggregation, unlike a plain `findMany` row scan), so `analyticsService.getRequestsByUser` fetches *every* matching group (`analyticsRepository.countRequestsByUser`, no `take`) and slices it in memory for `offset`/`limit` — same bounded-by-registered-user-count reasoning as the capped-list decision above, just extended from "cap at N" to "page N per page, page M." A `search` param resolves to matching user ids first (`userRepository.searchIds`, name/email `contains`, case-insensitive) and constrains the `groupBy`'s `where.userId: { in: [...] }`; a search matching zero users short-circuits before ever calling `groupBy`. This in-memory approach is specifically fine *here* because of that bound — it would be the wrong call for an ever-growing content list, where cursor pagination on a real `findMany` remains the right tool.

### Internal analytics: a session's journey interleaves page views with logged actions

`PageView` alone only shows which pages a user loaded, not what they *did* on them — a comment posted mid-visit was invisible in the journey view until this was added. `frontend/src/lib/api.ts`'s shared `request()` wrapper (and `uploadMedia`, which bypasses that wrapper) now attaches an `X-Session-Id` header, sourced from the same `sessionStorage` id `usePageViewTracking.ts` uses (factored out into `frontend/src/lib/analyticsSession.ts` so both call sites share one id). The `onSend` hook in `api.ts` reads that header into `RequestLog.sessionId` (nullable — Swagger/curl/tests never send it). `analyticsService.getSessionJourney` merges a session's `PageView` and `RequestLog` rows into one chronological `steps` list, each tagged `type: 'pageview' | 'action'`. The sort key matters: a page-view step sorts by its *entry* time (`createdAt - durationMs`), not the write-time `createdAt` (which is leave time) — otherwise an action taken mid-visit would sort *before* the page-view step it happened during, since the row for "having been on this page" isn't written until the user leaves. Two exclusions keep this list free of noise: `/auth/refresh` is never logged at all (the silent auto-refresh timer isn't a step the user took), and everything else already excluded from `RequestLog` (see "what RequestLog captures" above) stays excluded here too.

**Consecutive same-path page views are merged, not shown as separate visits.** The `hidden` visibility trigger described above (flush-and-reset on tab backgrounding, a safety net in case the tab gets killed while hidden) writes a `PageView` row even when the user hasn't navigated anywhere — just alt-tabbed away and back to the *same* page. Left alone, that produces two rows for what's really one continuous visit (confirmed live: switching tabs for ~18s mid-visit on `/` produced a 1025ms row and a 9196ms row, back to back, before the actual navigation away). `getSessionJourney` collapses any run of consecutive `pageview` steps sharing the same `path` into one, summing `durationMs` and taking the first `enteredAt` / last `leftAt` — but only when they're strictly adjacent in the sorted list. An `action` step (or a different path) sitting between two same-path page views breaks the run deliberately: that's a real event, not backgrounding noise, and collapsing across it would misrepresent when it happened relative to page time.

### Internal analytics: dashboard summary is grouped by topic, sourced from four different tables

`GET /analytics/summary` returns four groups — `users`, `posts`, `newsletter`, `backend` — each pulled from a different domain table, not just `RequestLog`/`PageView`: `users.totalAllTime`/`newInPeriod` from the `User` table, `posts.newInPeriod` from the `Post` table (any status, not just published — reflects authoring activity, not what's live), `posts.commentsInPeriod` from the `Comment` table (top-level and replies both count), and `newsletter.*` from the `Newsletter` table (unrelated to request/page-view tracking entirely). Only `posts.readsInPeriod` (a `PageView` count where `path` starts with `/posts/`) and `backend.requestsInPeriod` (a `RequestLog` count) come from the tracking tables — so `readsInPeriod` inherits the same registered-users-only limitation as the rest of this dashboard (an anonymous visitor reading a post is invisible here, same as everywhere else in this feature).

`newsletter.pending` completes the four-way split alongside `subscribed`/`unsubscribed`/`blocked` (all defined in `newsletterRepository.countForAnalytics()`) — with it added, the four buckets now partition every subscriber row exactly once and sum to the total row count, closing a gap the dashboard previously needed a UI footnote to explain.

### Internal analytics: newsletter period counters need their own timestamp, not `updatedAt`

`newsletter.subscribedInPeriod`/`unsubscribedInPeriod` add period-scoped deltas alongside the four all-time buckets above. `subscribedInPeriod` counts by `confirmedAt` falling in the range — not `createdAt`, which is when the subscribe form was submitted, possibly long before (or without ever) being confirmed. `unsubscribedInPeriod` needed a new `Newsletter.unsubscribedAt` column (migration `20260725114504_add_newsletter_unsubscribed_at`); the model had no field that could answer "when did this row become unsubscribed." A generic `updatedAt` (which `Newsletter` doesn't have, unlike `Post`/`Comment`) would have been the wrong fix even if added: it bumps on *every* write to the row, so a later admin block or a resubscribe would silently overwrite the real unsubscribe date, corrupting historical period counts. Instead `unsubscribedAt` follows the same dedicated-per-transition-timestamp pattern already established by `confirmedAt` and `blockedAt` — set only by `newsletterRepository.unsubscribe()` and `block()` (block also transitions status to `UNSUBSCRIBED`, so it sets the same field), and never touched by `subscribe()`/`confirm()`/`unblock()`. `countUnsubscribedBetween` excludes blocked rows (`blockedAt: null`), mirroring `countForAnalytics()`'s existing distinction between organic unsubscribes and admin-initiated blocks.
